# 로컬 Docker 시연 실행 정리 (2026-10-24)

## 요청과 기준

- 사용자 결정: 온라인 배포는 보류. Docker + PostgreSQL 기반 로컬 시연.
- 실행 방식은 하나. 기본 PB·고객·보유 종목·기업·공시를 준비하고, 나머지는 실제 API·MCP로 처리한다.
- 고정된 시연 DB 하나를 새 시연 시작 시 삭제·재생성한다. 실행 중에는 결과를 유지한다.
- 새 브랜치 `codex/local-docker-demo`, 기준 `codex/service-integration-release`의 `36182a8`.

## 구현과 판단 근거

### 전용 프로젝트와 DB

`docker-compose.demo.yml`, `start.ps1`, `start.sh`를 추가했다. Compose 프로젝트는 `dartch-local-demo`, DB는 `dartch_demo`로 고정했다.
순서: 빌드 → 시작 잠금 → 기존 시연 web/api/business/rag 중지 → postgres 준비 → API 검사 → DB 재생성 → Alembic → 기본 데이터 → 실제 사례 사실 → JWT 생성 → 서비스 시작.
임시 DB 이름이 계속 늘어나는 구조를 피했고, 다른 프로젝트의 영구 볼륨과 SQLite는 건드리지 않는다.
`prepare_demo.require_demo_target`은 정확한 호스트·계정·DB·체크포인트 URL 이외의 초기화를 거부한다.
DB 삭제 SQL은 상수로 한정하고 애플리케이션 사용자 입력으로 대상을 바꾸지 않는다.
시작 잠금은 동시에 두 시작 스크립트가 DB를 초기화하는 일을 막는다. 강제 종료로 남은 잠금의 복구 명령은 실행 문서에 적었다.

종료는 컨테이너를 중지하고 다음 시작 스크립트가 DB를 재생성한다. 같은 실행의 컨테이너 장애 재시작은 DB를 초기화하지 않는다.
DB와 PostgreSQL 체크포인터가 같은 `dartch_demo`를 사용하므로 지난 실행의 Graph 중간 상태도 이어받지 않는다.
컨테이너는 생성된 동일 JWT를 전용 session 볼륨에서 읽는다. 키를 이미지·Git에 넣지 않고 매 새 시연마다 변경한다.
PostgreSQL에는 호스트 포트를 공개하지 않는다. 고정 내부 접속 비밀번호는 이 격리된 로컬 시연에만 사용하는 값이다.
온라인 배포용 보안/데이터 수명 구성을 대신하지 않는다.

### 기본 자료와 실제 분석

기존 `scripts/data/seed_db.py`의 적재 함수를 재사용하되 빈 시연 DB에만 호출한다.
기본 테넌트는 마이그레이션이 이미 넣을 수 있으므로 merge한다(첫 검증에서 발견한 중복 PK 문제 수정).
PB 2명, 고객 20명, 보유 42건, 기업 5개, 공시 메타데이터 594건을 적재한다.
P01은 ADMIN으로 수집/분석을 실행하고 P02는 PB로 담당 고객 범위를 확인한다. 두 계정 비밀번호는 기존 공개 데모 값 `demo1234`다.
기본 회사의 과거 base_score/base_reasons는 비우고, 저장 원문은 DB에 넣지 않는다. 과거 기대 영향도/등급을 현재 판정으로 주입하지 않는다.

시작 시 위니아 부도 공시 `20231005000522`의 항목 API `dfOcr`를 실제로 호출한다.
날짜 범위만 믿지 않고 정확한 접수번호와 행 유일성을 확인한 뒤 기존 R3 build_payload/R4 store_facts·mark_ready를 사용한다.
원문은 RAG가 DART에서 가져오며, 설명과 안내문은 실제 OpenAI로 생성한다.
594건을 모두 자동 분석하면 비용·대기가 커지므로 기본 자동 인계는 1건으로 제한했다. 추가 실제 수집은 화면에서 가능하며 백필이 다수 분석을 만들 수 있음을 문서화했다.
이 선택은 모의 결과를 넣는 것이 아니라 실제 분석의 시작 범위를 제한하는 것이다.

### 환경변수 문제

기존 OpenAI 401은 `.env`의 키가 아니라 호스트 실행 환경에 있던 다른 `OPENAI_API_KEY`가 우선 적용된 결과였다.
같은 모델을 `.env` 키로 직접 조회하면 모델/임베딩 메타데이터 모두 성공했다. DART도 성공했다.
새 Compose는 API 키를 `${OPENAI_API_KEY}`로 보간하지 않고 서비스 `env_file: .env`에서 직접 받는다.
따라서 호스트 셸의 오래된 키가 컨테이너 키를 덮어쓰지 않는다. 내부 DB/Graph/큐/trace 설정은 Compose에서 실제 시연 값으로 고정한다.
`.env.example` 기본 모델과 로컬 `.env`의 LLM_PRIMARY를 `gpt-5.4-mini`로 정리했다. 실제 키는 변경·출력·커밋하지 않았다.
Anthropic 키가 비어 있을 때 fallback으로 가는 기존 모델 선택 코드는 유지한다.

### 실행·화면·문서

- Windows: `.\start.ps1`, macOS/Linux: `sh ./start.sh`. 호스트 Python/uv/Node/PostgreSQL 별도 설치 불필요.
- `scripts/ops/run_stack.py`는 동일 Docker 시작 스크립트로 전달하는 호환 진입점으로 바꾸고 이전 --fake/--demo/포트 옵션은 받지 않는다. 포트는 .env로 설정한다.
- 로그인 데모 계정 버튼은 적재되는 계정과 동일하다. 화면에 로컬 시연·실제 API·재실행 초기화 안내를 넣었다.
- README, CLAUDE, 실행 문서, DB 수명 계약, 검증 문서를 갱신했다. 이전 실행 절차는 legacy에 보존했다.
- 기존 docker-compose.yml 영구 저장 구성은 기록/개발을 위해 남겼으며 현재 사용자용 시작 경로가 아님을 명시했다.

## 검증의 한계와 현재 상태

- macOS Docker 엔진에서 시작 스크립트의 전체 경로를 실행했다. Windows PowerShell 실행은 이 환경에서 직접 검증하지 못했다. PowerShell 스크립트는 인코딩 문제를 줄이도록 ASCII 메시지를 사용했다.
- 브라우저 도구의 이전 접근 거부를 우회하지 않았다. 화면 빌드/HTTP/API 연계는 확인했으나 실제 화면 클릭 자동화나 시각 검증을 완료했다고 표현하지 않는다.
- 자동 공시 수집 전체/모든 공시 유형/모든 재작성 분기는 이번 실제 사례 1건 검증 범위를 넘는다. 관련 기존 회귀 테스트는 통과했다.
- Docker 엔진의 기존 credential helper가 멈추는 환경 문제 때문에 검증 명령에서만 별도 임시 Docker client config를 사용했다. 사용자 Docker 설정은 변경하지 않았다.
- 현재 Docker 시연 서비스는 실행 중이며 마지막 새 시연은 기본 분석만 완료하고 승인·업무는 0건인 상태다.
- 이번 변경은 아직 커밋/푸시하지 않았다.


## 후속 실행·테스트·코드 검토 (사용자 최종 검증 요청)

### 검토에서 발견하고 수정한 점

1. 시작 잠금을 빌드 후에 잡으면 다른 시작 프로세스가 공용 이미지 태그를 교체할 수 있었다. 잠금을 빌드 앞으로 이동했다. 잠금 컨테이너는 볼륨을 선언하지 않는 python:3.11-slim 이미지를 사용해 익명 PostgreSQL 볼륨도 생성하지 않는다.
2. 기본 dfOcr 자료를 DB 초기화 후 조회하던 순서는 외부 응답 오류 시 이전 DB부터 잃게 했다. 조회·접수번호 유일성·StructuredFacts 스키마 검증을 삭제 전에 수행하도록 분리했다. OpenAI/DART 사전 검사 실패와 기본 공시 조회 실패 모두 DB 접속/삭제로 진행하지 않는 회귀 시험 2건을 추가했다.

### 실제 기능 재검증

수정된 시작 스크립트로 빌드·DB 초기화·기동을 실행했다. 시작 중 두 번째 스크립트는 코드 1로 종료되고 빌드/초기화로 진행하지 않았다.
실제 위니아 분석 DONE/RED → 실제 안내문 생성 → P01 재작성 요청 → 실제 모델 재작성 → 승인 대기로 복귀 → 승인 두 번 → 업무 1건을 확인했다.
P02는 담당 초안 2건 중 1건 반려·1건 승인하여 업무 1건만 생겼다. 타 PB 고객 승인 및 업무 상태 변경은 403이었다.
P01 업무의 보류→연락완료 처리와 종목 확인함 요청도 200이었다.
백엔드 이미지 안에 .env와 data/release.env가 없는 것도 확인했다.
