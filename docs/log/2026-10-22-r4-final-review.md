## 정적 검토에서 확인한 충돌·복구 위험

### 수집 예약의 프로세스 장애 복구

`api/routes/collect.py:54`는 수집 실행 전달 전에 PENDING 작업과 종목 예약을 commit한다. commit 후 전달 전 프로세스가 종료되거나 실행자가 사라지면 예약 해제·리스 만료·재전달 경로가 없다. 같은 회사의 후속 요청은 기존 PENDING을 반환하고 다른 실행은 해당 종목을 예약할 수 없어 수집이 멈출 수 있다. R3 dispatcher 연결 전에 지속 실행 인계·만료·복구 정책을 구현해야 한다. 실제 프로세스 종료 실험은 수행하지 않았다.

### R3와의 테이블 정의 충돌

R3 카드는 shared/models/collect.py에 financial_snapshots·collect_runs를 작성하도록 되어 있으나 현재 R4는 operations.py에 두 테이블을 정의했다. 두 파일이 모두 shared.models에서 import되므로 R3가 같은 테이블을 별도로 선언하면 SQLAlchemy 중복 테이블 오류가 발생한다. 단일 모델 정의 위치를 계약으로 고정해야 한다.

### 담당 경계·Git

- 로컬 `origin/main`은 HEAD의 조상이다. 해당 스냅샷 기준 텍스트 병합 충돌은 없다. 원격 최신 상태를 fetch하지 않았고 다른 사람의 미공유 변경까지 확인한 것은 아니다.
- `.dockerignore`, `alembic.ini`는 CODEOWNERS 기본 규칙상 R1이다. 구현에 필요한 파일이지만 R4 소유 예외가 없어 리뷰 담당 정리가 필요하다. 요청한 로그·결정 문서도 R1 기본 규칙에 포함된다.
- R2/R3/R5의 소스 파일을 직접 수정한 것은 없다. 다만 R4가 새 계약을 추가한 뒤 상대 담당자의 확인을 받았다는 기록은 없다.
- Agent→risk_engine 직접 import는 기존 assembly/rules에 남아 있다. 이번 커밋에서 새로 만든 위반은 아니지만 팀의 의존 방향과 맞지 않아 연결 계약 정리 때 확인해야 한다.

## 도구 사용 검토

- 이번 검증은 로컬 파일·Git·임시 DB·테스트만 사용했다. 유료 모델·DART 외부 호출·외부 메시지·운영 DB 변경은 없었다.
- Agent의 변경 도구는 현재 코드 경로에서 호출하고 모델의 자유 선택 대상으로 제공하지 않는 구조를 확인했다. get_holders의 고객 이름 마스킹과 회사 필터도 유지된다.
- 과거 근거 재검증은 위 1번처럼 도구 결과 계약이 깨져 있다. 이를 “근거가 확인된 정상 호출”로 통합 판정할 수 없다.
- 새 save_risk_state는 전달된 stage·점수·해소 근거를 저장하며 자체 재계산은 하지 않는다. 신뢰된 코드만 호출한다는 경계를 유지하고, 향후 LLM 도구 선택에 노출하지 않아야 한다.
- create_contact_task의 PB 승인 증명은 Graph와 adapter가 담당한다. 도구 자체는 평가 상태·보유·중복만 검사하고 고객별 승인 기록을 검사하지 않는다. 현재 API 경로의 승인 검사는 확인했지만, 다른 MCP 호출자가 생길 경우 동일 보장을 전제로 하면 안 된다. 기존부터의 신뢰 경계다.
- release_disclosure_index·purge_disclosure_text는 현재 호환 경로에 남아 있다. R3의 메모리 RAG 연결 시 제거·대체할 명시적 과제이며, 현재의 호출 근거는 기존 ephemeral 정리 계약이다.

## 권장 처리 순서

1. 1~4번의 근거·상태 최신성·승인·점수 노출 문제를 우선 수정하고 회귀 테스트를 추가한다.
2. 5번의 R2/R4 실행 계약, R3 모델 정의 위치와 재무 입력 선택을 합의한다.
3. 6~9번 및 수집 예약 복구를 보완한다.
4. 회사별 실행과 실제 데이터 수집을 연결한 뒤 전체 통합·실제 사례 평가를 수행한다.

기존 267개 통과는 회귀 안정성의 일부 증거다. 위 재현 사례를 포함하기 전에는 요구사항 전체의 완료 근거로 사용하지 않는다.
