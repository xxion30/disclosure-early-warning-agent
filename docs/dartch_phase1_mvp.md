# DARTCH Phase 1 MVP 설계서 (초안)

> 상태: **초안 — 팀 확인 전.** `[가정]`은 제가 정한 가정이고, `[확인 필요]`는 아직 모르는 것입니다.
> DARTCH는 임시 이름입니다. 회의록(10/22 오전·오후)과 이후 결정 사항을 반영했습니다.

## STEP 01. 문제 정의

### 한 줄 정의
PB가 고객 보유 종목의 위험을 판단하려고 공시를 일일이 열어 읽던 일(노가다)을 AI가 대신해서, **위험 경보와 그 근거**를 웹 화면으로 알려 주는 B2B2E 서비스.

### 풀려는 문제
- 공시는 종류가 많고 길어서, PB가 고객 보유 종목마다 위험 신호를 손으로 찾아야 한다.
- 위험은 공시 한 건이 아니라 **여러 공시와 재무 수치가 겹쳐서** 나타난다(예: 유상증자 + 자본잠식).
- 목적은 **손실 방지**다. 주가 상승 가능성은 보지 않는다(잃지 않는 것이 먼저).

### 사용자
- B2B2E: 증권사(기업)에 제공하고, 그 회사의 **PB(직원)** 가 쓴다.
- PB는 자기 고객이 보유한 종목의 위험만 본다.

### 하지 않는 것 (Phase 1)
- 고객에게 연락하는 기능(안내문 초안, 연락 업무, PB 승인 단계) — **삭제**
- 뉴스·SNS 수집, 선행성 검증 — **제외** (SNS는 현업에서 유료로 확장하는 후속 과제)
- 채권(회사채 등) 분석 — **제외**, 주식만
- 주가 상승·매수·매도 추천, 주가 예측
- 이메일·메신저 알림 — 웹 화면만 (Phase 2 후보)

### 성공 기준 (MVP 완료 기준)
1. 매일 오전 9시 5분에 자동으로 수집이 한 번 돌고, 수집 이력(시각·건수·성공 여부)이 남는다.
2. 수집 대상은 **PB 고객이 보유한 종목만**이다 (보유하지 않은 종목은 조회하지 않는다).
3. 🔴 항목이 한 가지만 나와도 경보가 뜬다.
4. 🟠·🟡는 가중치 점수로 경보 / 복합 위험 / 관찰 중 / 없음이 판정된다.
5. 화면에서 경보의 **근거**(DART 값 또는 원문 인용 + DART 링크)를 확인할 수 있다.
6. 정정·철회·후속 공시가 반영되어 위험이 커졌는지 풀렸는지 표시된다.
7. 테스트 사례 세트로 평가표(경보 적중, 경보 빈도)가 만들어진다.

## STEP 02. 범위와 요구사항

### 서비스 흐름
```
09:05 시작
→ ① 고객 보유 종목 읽기 (PB들의 보유 종목 합집합, 중복 제거)
→ ② 종목코드 → DART 회사 코드 변환
→ ③ 종목별로 "지난 수집 이후" 접수된 공시·재무 정보만 조회 (증분)
→ ④ 위험 항목 분류 (제목/API 항목 → 본문 → 재무 수치 순서로 확인)
→ ⑤ 단계 판정 (🔴 / 🟠 / 🟡 / 복합 / 관찰 / 없음)
→ ⑥ AI가 근거를 인용해 설명 → 저장
→ ⑦ 웹 화면에 반영 (새 경보 표시, 종목별 위험 상태)
```

### 위험 항목 (회의록 기준)

**🔴 즉시 경보** — 한 가지만 나와도 경보 (점수 계산 없음)
| 항목 | 위험 이유 |
| --- | --- |
| 부도발생 | 원리금 미상환, 주주가치 손실 |
| 회생절차 개시신청 | 채무조정·상환 지연·주주가치 훼손 |
| 채권은행 등의 관리절차 개시 | 재무위기·구조조정 신호 |
| 해산사유 발생 | 청산, 잔여재산 회수 불확실 |
| 영업정지 | 매출·현금흐름 감소. 정지 기간과 해당 사업 매출 비중으로 심각도 표시 |
| 거래정지 | 매매 불가, 상장 유지 위험 (거래소 공시, 제목으로 감지. 분할·합병·액면 변경 등 행정적 정지와 정지 해제 공시는 제외) |
| 관리종목 지정 | 상장폐지 우려 (거래소 공시, 제목으로 감지) |
| 국내 상장폐지 사유 발생 | 상장 유지 불확실 (거래소 공시, 제목으로 감지. 해외 상장폐지와 구분) |
| 횡령·배임 혐의 발생 | 회사 신뢰·재무 훼손 (거래소 공시, 제목으로 감지. **금액 기준 없이** 한 건만 나와도 경보) |

**🟠 내용 분석 후 경보** — 규모·목적·조건을 확인해 점수 계산
| 항목 | 확인할 것 |
| --- | --- |
| 소송 등의 제기 | 자기자본 대비 청구액, 핵심 영업 영향 |
| 감자 결정 | 결손 보전 목적 여부, 주주가치 훼손·현금 유출 |
| 유상증자·유무상증자 | 희석 규모, 반복 조달, 납입 지연·실패 |
| CB·BW·EB 발행 | 잠재 주식 공급, 발행조건, 조기상환 부담 |
| 영업·자산·타법인 지분 양수도 | 핵심자산 매각, 과도한 인수, 차입 확대 |
| 자산양수도·풋백옵션 | 환매·매입 의무에 따른 현금 유출 |
| 합병·분할·주식교환·이전 | 부실 이전, 불리한 교환비율 |
| 자기주식 처분·취득 신탁계약 해지 | 긴급 자금 확보 여부, 주식 공급 부담 |
| 채권은행 관리절차 중단 | 정상화인지 협의 실패인지 |
| 해외 상장폐지 | 부실·규정 위반 여부 (국내 상장폐지와 구분) |

**🟡 재무 추세 경보** — 정기보고서·재무제표에서 추적, 점수 계산
| 항목 | 확인할 것 |
| --- | --- |
| 감사의견 | 한정·부적정·의견거절, 계속기업 불확실성 (**🟡 유지로 결정**) |
| CP·단기사채·회사채 미상환 잔액 | 단기 만기 집중, 차환 부담 |
| 채무증권 발행실적 | 조달금리 상승, 만기 단기화 |
| 공모·사모자금 사용내역 | 조달 목적과 실제 사용의 차이 |
| 최대주주 변동·타법인 출자 | 지배구조 불안, 관계사 부담 |
| 전체 재무제표 | 자본잠식, 영업현금흐름 적자 지속, 이자 부담 증가, 현금 대비 단기채무 증가 |

### 판단 원칙 (회의록 6번)
1. 주가(주주가치)에 미치는 영향 기준으로 평가한다 (예: 유상증자는 희석 요인이라 위험 신호).
2. **제목 → 본문 → 재무 수치** 순서로 확인하고, 금액·기간·사유를 반영한다.
3. 공시 검색과 원문 분석을 함께 한다. 횡령·배임, 채무보증, 원리금 미지급, 주요 계약 해지도 포함한다. [확인 필요: 이 항목들이 위 세 단계 중 어디에 속하는지]
4. 정정·철회·후속 공시를 반영해 위험이 커졌는지 풀렸는지 추적한다.

### 판정 규칙

**경보 판정 순서**
| 순서 | 조건 | 결과 |
| --- | --- | --- |
| 1 | 🔴 항목이 한 가지라도 있음 | 🔴 즉시 경보 |
| 2 | 🟠 점수 4점 이상 | 🟠 경보 |
| 2 | 🟡 점수 5점 이상 | 🟡 경보 (🟠과 동시에 가능) |
| 3 | 위에 모두 해당 안 함 + (🟠점수÷4) + (🟡점수÷5) ≥ 1.5 | 🟠 경보, 사유 "복합 위험" |
| 4 | 위에 모두 해당 안 함 + 🟠 3점 이상 또는 🟡 4점 이상 | 관찰 중 (알림 없음, 화면 표시만) |
| 5 | 그 밖 | 경보 없음 |
- 화면 맨 위에는 가장 심한 단계(🔴 > 🟠 > 🟡)를 보여 준다.
- 기준값(4, 5, 1.5, 75%)은 **초안**이다. 기존 5개 회사 공시와 새 테스트 사례로 경보 빈도를 보고 조정한다.

**🟠 점수표 (초안)** — 점수 = 기본점수 + 내용 보정 + 반복 보정. 12개월 동안만 유효, 6개월이 지나면 50% 반영.
| 항목 | 기본 | 내용 보정 (+점수) |
| --- | --- | --- |
| 소송 제기 | 1 | 청구액이 자기자본 대비 1% 이상 +1, 5% 이상 +2, 10% 이상 +3 / 핵심 영업 관련 +1 |
| 감자 결정 | 2 | 결손 보전 목적 +1 / 감자 비율 50% 이상 +1 |
| 유상증자 | 2 | 발행 비율 20% 이상 +1, 50% 이상 +1 / 제3자배정 +1 / 12개월 내 반복 +1 / 납입 지연·실패 후속 공시 +2 |
| CB·BW·EB 발행 | 2 | 리픽싱 조항 +1 / 12개월 내 2회 이상 +1 / 조기상환 청구권 +1 |
| 영업·자산·타법인 양수도 | 1 | 거래 규모가 자기자본 대비 10% 이상 +1, 30% 이상 +2 / 핵심자산 매각 +1 |
| 자산양수도·풋백옵션 | 2 | 환매·매입 의무 금액이 자기자본 대비 10% 이상 +1 |
| 합병·분할·주식교환 | 1 | 교환비율 불리 근거가 본문에 있음 +2 / 부실 이전 +2 |
| 자기주식 처분·신탁해지 | 1 | 긴급 자금 확보 목적 명시 +2 |
| 채권은행 관리절차 중단 | 1 | 협의 실패·종결 사유 +3 (정상화면 0) |
| 해외 상장폐지 | 1 | 부실·규정 위반 사유 +3 |

**🟡 점수표 (초안)** — 최신 정기보고서 기준, 보고서가 갱신될 때만 다시 계산.
| 지표 | 점수 구간 |
| --- | --- |
| 감사의견 | **거절·부적정 +5 (단독으로 🟡 경보)** / 한정 +3 / 계속기업 불확실성 +3 |
| 자본잠식 | 50% 이상 +3, 전액 +4 |
| 영업현금흐름 | 적자 1년 +1, 2년 연속 +2 |
| 이자 부담 | 이자보상배율 1 미만 +2 |
| 단기 채무(CP·단기사채·회사채, 1년 이내 만기) | 현금성자산 대비 100% 이상 +2, 200% 이상 +3 |
| 채무증권 발행 | 발행 금리 전년 대비 상승 +1 / 평균 만기 단기화 +1 |
| 자금 사용내역 | 조달 목적과 실제 사용 불일치 +2 |
| 최대주주 변동·타법인 출자 | 12개월 내 최대주주 변경 +2 / 출자 규모가 자기자본 대비 큼 +1~2 |

**반복·해소**
- 경보는 공시마다가 아니라 **종목당 "위험 상태" 하나**로 묶고, 개별 공시는 그 아래 시간순으로 쌓는다.
- 새 알림(화면의 "새 경보" 표시)은 **단계가 올라갈 때 / 새 종류의 근거가 추가될 때 / 🔴이 새로 생길 때**만 낸다.
- 위험이 풀리는 것은 **확인된 해소 공시**(철회·취소·정상화 확정 등)가 있을 때만 "해소됨 + 근거 링크"로 표시한다. 이력은 남기고, 불확실하면 위험을 유지한다(보수적).
- PB의 "확인함" 표시는 읽음 표시일 뿐 경보를 닫거나 승인하지 않는다.

**점수 숫자는 모두 `rules.yaml` 한 곳에만 둔다.** 코드를 바꾸지 않고 담당자가 조정할 수 있게 하기 위해서다(이전 프로젝트와 같은 원칙).

### 이전 항목 중 Phase 2로 미루는 것
- 정기보고서 제출 지연, 감사인 변경, 호재 공시 정정·해지, 최대주주 주식 담보, 같은 공시 3회 이상 정정(별도 신호), 사업보고서 기본 점수 중 새 🟡 지표에 없는 항목은 Phase 1에서 `rules.yaml`에 넣지 않는다 (git 이력에 남아 있어 나중에 다시 쓸 수 있다).
- **종속회사 공시는 본사 점수에서 제외**한다. 제목에 "(종속회사의주요경영사항)"이 붙은 소송·감자·영업정지·합병 등은 본사 위험이 아니기 때문이다 (이전 프로젝트와 같은 규칙).

## STEP 03. 데이터 (수집과 출처)

### 원칙
- 데이터 출처는 **OpenDART 공식 API만** 쓴다. 표를 화면 긁기로 가져오지 않는다.
- **구조화된 값(API 필드) 우선**, 텍스트 필드(사유·내용)만 AI가 해석한다. [가정 — 아래 "API 확인"에서 검증]
- 모든 값에는 출처(API 이름, 접수번호, 필드명, 가져온 시각)를 기록한다.

### 수집 방식
| 항목 | 내용 |
| --- | --- |
| 주기 | 매일 오전 9시 5분 1회 (KST). 주기 고민은 남겨 두고 한계를 문서에 적는다 |
| 대상 | PB 고객 보유 종목의 합집합(**ETF·펀드 제외**). 종목 단위로 한 번만 조회 |
| 증분 | "마지막으로 성공한 수집 시각 이후 접수된 공시"만 조회. 주말·휴일·실패로 건너뛴 날도 이어서 받는다 |
| 새 종목 | 보유 목록에 처음 들어오면 최근 12개월 공시와 최신 정기보고서를 한 번에 받아 채운다(백필) |
| 보유 종료 | 수집을 멈추고 이력은 남긴다 |
| 실패 | 종목별로 재시도, 한도 초과·장애는 수집 이력에 남기고 화면에 "마지막 수집 시각"을 표시 |
| 한계 | 장중에 나온 공시는 다음날 오전에야 알게 된다 (문서와 화면에 명시) |

| 그룹 | 쓰일 위험 항목 |
| --- | --- |
| 공시검색 (`list`) | 새 공시 발견, 정정·철회 추적, 접수번호·DART 링크. **🔴 거래소 공시(거래정지·관리종목·상장폐지·횡령·배임)는 이 제목으로 감지**하고 필요하면 원문을 읽는다 (정리된 값 API가 없을 가능성이 있음, R3 확인) |
| 주요사항보고서 주요정보 | 🔴 부도·영업정지·회생·해산·관리절차 개시, 🟠 소송·감자·유상증자·CB/BW/EB·양수도·합병분할·자기주식·관리절차 중단·해외 상장폐지 |
| 정기보고서 주요정보 | 🟡 감사의견, 단기사채·CP·회사채 미상환 잔액, 채무증권 발행실적, 공모·사모자금 사용내역, 최대주주 변동, 타법인 출자 |
| 재무정보 | 🟡 자본잠식, 영업현금흐름, 이자보상, 현금 대비 단기채무 (이미 `scripts/compute_base_score.py`가 `fnlttSinglAcntAll`을 부르고 있음) |
- **확인할 것**: ① 항목별로 어떤 필드를 주는지 ② 각 항목을 회사 코드 단위로 조회할 수 있는지 ③ 하루 호출 한도(초과 시 응답 코드) ④ 보고서 제출 후 재무 값이 반영되기까지 시차 ⑤ 정정 공시가 같은 값을 덮어쓰는지 별도로 오는지.
- API가 주지 않는 항목(예: 소송의 핵심 영업 관련 여부, 합병비율 불리 판단)은 **원문 텍스트를 읽어 AI가 플래그만 뽑는다**(근거 인용 필수).

### 보관
- 공시 원문은 처리 중에만 임시 색인하고, 경보를 저장한 직후 색인과 DB 본문을 지운다(이전 프로젝트에서 구현한 운영 모드 `RAG_INDEX_MODE=ephemeral`을 기본으로 사용 [가정]).
- 남기는 것: 접수번호, 제목, 접수일, DART 링크, 원문 해시, 판정 값, 근거 문장·위치.

## STEP 05. AI 처리 흐름

### 원칙
- **점수·단계는 규칙(코드)이 정한다. AI는 바꿀 수 없다.** AI는 (1) 텍스트에서 플래그를 뽑고 (2) 근거를 인용해 설명한다.
- 모델 출력은 JSON 형식으로 받고 Pydantic으로 검사한다. 근거 인용은 **원문에 글자 그대로 있는지** 코드가 확인한다.
- 근거를 못 찾으면 추측하지 않고 "수동 확인 필요"로 남긴다.

### 그래프 (예상)
```
receive(공시·API 값 불러오기) → classify(위험 항목 매핑)
  ├ 🔴 항목 → mark_red ───────────────────────────────┐
  ├ 🟠 항목 → extract_flags(AI, 텍스트 필드만) → score_orange ┤
  └ 🟡 항목/정기보고서 → compute_indicators(코드) → score_yellow ┤
                                                      judge_stage(규칙: 복합·관찰 포함)
                                                      → explain_risk(AI, 근거 인용 필수)
                                                      → save_state → END
오류·한도 초과 → handle_failure → MANUAL_CHECK
```
- 이전 그래프에서 **삭제**: `find_customers`(연락 우선순위), `draft_messages`, `guardrail_check`(안내문), `pb_approval`(interrupt), `create_tasks`, `save_rejection`, `finalize`.

### AI가 하는 일과 출력 형식
| 단계 | AI 입력 | AI 출력(Pydantic) |
| --- | --- | --- |
| extract_flags | 해당 항목의 텍스트 필드(사유·내용)와 검색 조각 | `flags: [{flag, value, evidence[{source, quote, rcept_no, location}]}]` — 예: `결손보전목적=true`, `핵심영업관련=true` |
| explain_risk | 점수 내역(규칙이 계산한 것)과 근거 | `items: [{breakdown_index, explanation, evidence[]}]` — 점수 항목마다 한 문장 설명 |
- 점수·단계 필드는 출력 형식에 **아예 없다.**

### 프롬프트 (R2 산출물)
`system.md`, `extract_flags.md`(신규), `explain_risk.md`(수정), `select_tools.md`(유지). 삭제: `draft_message.md`, `rewrite_message.md`. 각 파일 맨 위에 `version: vN`을 두고 바꿀 때마다 올린다.

### Harness 8요소 (유지·변경)
| 요소 | 변경 |
| --- | --- |
| Instructions | 프롬프트 새로 작성, 버전 관리 유지 |
| Tools | 읽기 전용 도구 선택(최대 2회전) 유지. 변경 도구는 코드만 호출 |

## STEP 06. 검증과 평가

### 테스트 사례 세트 (R6가 "평가용 질문 세트" 대신 사용)
- 형식: `(종목, 기준일, 기대 단계, 기대 근거 공시/항목)`
- **실제 DART 과거 사례만** 쓴다(공시 내용·접수번호를 지어내지 않는다). 단계마다 사례를 모은다.
  | 단계 | 필요한 사례 |
  | --- | --- |
  | 🔴 | 부도·회생·영업정지·해산 중 실제 사례 (항목당 1건 이상) |
  | 🟠 | 유상증자, CB/BW, 감자, 소송 등 (기준 점수 경계 근처 사례 포함) |
  | 🟡 | 감사의견 거절·한정, 자본잠식, 영업현금흐름 적자 지속 |
  | 정상 | 같은 기간 위험이 없는 회사 (경보가 안 울려야 함) |
- 이전 프로젝트의 5개 회사(금양·위니아·오스템임플란트·CJ CGV·SK)는 **회귀 사례**로 재사용한다.

### 지표
| 지표 | 의미 |
| --- | --- |
| 적중 | 사건이 있는 사례에서 기대 단계 이상이 울렸는가 |
| 경보 빈도 | 종목당 주당 경보 수 (알림 피로 확인) |
| 오탐 | 정상 사례에서 울린 경보 수 |
| 근거 정확도 | 근거 인용이 원문에 글자 그대로 있는 비율 |
| 수집 안정성 | 수집 성공률, 증분 누락 여부 |

### 개선 전후 비교 (예)
기준값(4·5·1.5·75%) 변경 전/후, 복합 규칙 켬/끔, 관찰 표시 켬/끔, 기본/대체 모델.

| 프론트엔드 | Vue 3 | **그대로 유지** (차트 라이브러리는 쓰지 않음, 추세는 표로 표시) | 선택 항목 제외 결정 | 변경 없음 |
| QA | pytest | **그대로 유지** (Playwright는 쓰지 않음. 시연 영상은 화면 녹화로 촬영) | 선택 항목 제외 결정 | 변경 없음 |
| 배포 | `run_stack.py` | **docker compose** (postgres, api, collector, mcp 서버 2개, web). `run_stack.py`는 로컬 개발용으로 유지 | 서비스가 늘어서 한 번에 띄워야 한다 | 필수 |
| Agent | LangGraph(승인 대기 포함) | LangGraph 유지(상태 저장·재시도). 승인(interrupt)은 쓰지 않는다 | R2 업무이고 재시작 후 이어 하기에 유용 | 변경 작음 |
| MCP | FastMCP, business·rag | 유지. social-mcp는 만들지 않는다 | SNS 제외 | 변경 없음 |
| 관측 | LangSmith | 유지 + 수집 이력(`collect_runs`) + `/health` | 수집 실패를 화면에서 확인 | 작음 |

**바꾸지 않는 것**: Vue→다른 프레임워크, LangGraph 교체, MCP 제거 같은 큰 교체는 이번에 하지 않는다. 이유는 이번 변경의 핵심이 데이터 수집과 판정 규칙이지 프레임워크가 아니기 때문이다.

5. **평가·마무리**: 테스트 사례 평가, 점수 기준 조정, 영상, README, 발표

### 회사 분리 (결정됨: 필요) / SSO (하지 않음)
- **회사(테넌트) 분리**: 증권사마다 PB·고객·보유 종목이 다르므로 `tenant_id`로 구분한다. API는 로그인한 사용자의 회사 데이터만 돌려주도록 한 곳에서 자동으로 걸러낸다.
- **공시는 공유**: DART 공시와 종목별 위험 판정은 공개 데이터 기반이라 회사 간에 공유하고, 수집은 **모든 회사의 보유 종목 합집합**(ETF 제외)을 한 번만 조회한다(호출 절약).
- **로그인**: 연동할 사내 인증 시스템이 없으므로 SSO는 하지 않는다. 이전 프로젝트의 이메일·비밀번호 로그인(JWT + bcrypt)을 그대로 쓰고, 사용자는 어느 회사 소속인지 함께 저장한다.
