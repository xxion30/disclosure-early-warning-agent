## 시작 전 규칙
- `main`을 pull한 뒤 `feat/r<번호>-<기능>` 브랜치를 따서 시작한다.
- **다른 사람 파일은 고치지 않는다.** 필요하면 PR 코멘트나 팀 채팅으로 요청한다. 담당은 [CODEOWNERS](../../.github/CODEOWNERS)가 정본이다.
- **계약(DB·API·MCP·State·규칙 구조)을 바꿀 때는 코드보다 `docs/contracts/` 문서를 먼저 고치고** 상대 담당의 OK를 받는다.
- `uv run pytest -q`가 통과해야 PR을 합친다. 점수 숫자는 `risk_engine/rules.yaml` 한 곳에만 둔다.
- 공시 내용·접수번호·숫자를 지어내지 않는다. 모르면 `TODO(확인 필요)`.

## 작업 순서 (일정은 R1이 정한다)
1. **0단계 계약 확정 (모두, 짧게)** — 아래 3개를 먼저 맞춘다. 이게 끝나야 병렬로 돈다.
   - ① `rules.yaml` 구조(🔴/🟠/🟡·복합·관찰) — R4 초안 → R2·R1 확인
   - ② 재무 지표 표(`financial_snapshots`)와 수집 데이터 형식 — R3 초안 → R4 확인
   - ③ State와 API 응답(점수 비노출, 정렬, `?alert=true`) — R4·R2 → R5 확인
2. **병렬**: R3 API 확인 → 수집기 / R4 규칙·DB·API / R2 그래프·프롬프트 (가짜 도구로) / R5 화면 (가짜 데이터로)
3. **통합**: 종목 1개로 수집 → 판정 → 안내문 → PB 승인 → 화면이 끝까지 도는지 확인 (R5 시연 시나리오)
4. **확장**: 🔴🟠🟡 전체 항목, 복합·관찰, 해소·반복
5. **평가·마무리**: 테스트 사례 평가, 기준값 조정, 영상, README, 발표

## 지금 코드가 어디까지 되어 있나
- 구조 정리와 고객 연락 기능 복원은 끝났다 (분석 → 설명 → 안내문 → PB 승인 → 연락 업무가 이전 규칙(Low~Critical)으로 돈다. 테스트 230개 통과).
- 연락 대상은 보유 고객 전원. 화면·API에 점수 숫자는 없고, 경보 알림은 등급 → 점수 → 최근 순으로 정렬된다.
- **아직 이전 프로젝트 그대로인 것**: 위험 규칙(A·B그룹, Low~Critical), 데모 데이터(`data/demo_companies.json`, `rag_docs/companies/`), SQLite·Chroma 저장. 이것을 새 설계(🔴/🟠/🟡, 수집기, PostgreSQL, 메모리 색인)로 바꾸는 것이 각 카드의 일이다.
